# Оценка реальной модели

Это необязательное LLM-расширение. Для бесплатного демо «Полотно» используйте `python evals/free_run.py`: он проверяет 40 локальных запросов и 20 фотокарточек, не требует ключа и не вызывает модель. Платный прогон ниже не является условием готовности бесплатной витрины.

`cases.json` — заранее заданный набор из 40 украинских запросов к неизменённому
`examples/catalog.csv`: 20 однозначных, 10 неоднозначных, 10 неизвестных/вне темы.
Схема действия: `product` — один проверенный SKU, `clarify` — уточнение среди
`expected_skus`, `not_found` — отсутствие товара без выдуманной карточки,
`handoff` — переход к менеджеру. Цена и остаток не должны генерироваться моделью.

Статус: **реальный прогон не выполнен**. Без разрешения владельца на API-расходы
не вызывайте Anthropic. Автоматические тесты с подменой модели не заменяют оценку.
Набор нельзя использовать для настройки промпта. При изменении промпта после
просмотра ошибок следующий честный контроль требует нового отложенного набора.

## Исполняемый runner

После установки проекта из корня репозитория выполните:

```powershell
python evals/run.py
```

По умолчанию проверяются только структура всех 40 случаев, импорт демонстрационного
каталога во временную БД и существование ожидаемых SKU. API-клиент не создаётся.
`.env` runner не читает; переменные должны уже находиться в окружении процесса.
Telegram-токен и ID менеджера ему не нужны.

Только после разрешения на расходы задайте `LLM_ENABLED=true`,
`ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`, положительные `LLM_DAILY_BUDGET_USD`
и все четыре тарифа из `.env.example`. Используйте отдельный бюджет оценки:
счётчик runner не является общим с запущенным ботом. Затем явно разрешите этот
прогон и укажите новую папку (существующая папка отклоняется):

```powershell
python evals/run.py --allow-paid --output evals/results/run-2026-10-17
```

Реальные запросы проходят через `LLM.resolve` и поиск в отдельном временном каталоге.
Каждый запрос имеет пустой контекст. Неизвестный исход API удерживает резерв
в `budget.sqlite3` отчёта. `cost_usd` включает такие резервы; точная стоимость
неизвестного исхода не заявляется. Usage с неполными данными помечается
`usage_complete=false`; бюджет/контекст без вызова — ошибка случая. Ошибки
провайдера сохраняются только по имени класса, без потенциально секретного текста.
При прерывании частичный JSONL сохраняется, метаданные имеют статус `incomplete`.

Runner проверяет решения и серверные карточки. `facts_pass` подтверждает наличие
SKU в каталоге и формирование карточки серверным шаблоном; отдельные автоматические
тесты фактических полей остаются обязательными. Он не проверяет доставку Telegram
и не выдаёт локальный переход `handoff` за доставленное обращение менеджеру.
Код завершения: 0 — офлайн-валидация либо достигнут порог реального прогона;
1 — порог не достигнут; 2 — неверные параметры/конфигурация.

## Порядок прогона

1. Зафиксировать commit или хеш исходников, SHA-256 каталога, набора и промпта,
   модель, версии зависимостей, дату UTC, настройки токенов, тайм-аутов и тарифы.
2. После разрешения установить отдельный бюджет прогона. Не использовать реальные
   сообщения клиентов и не помещать ключ в отчёт. Каждый случай начинает новый
   диалог с пустым контекстом; порядок и набор не меняются после начала прогона.
3. Для каждого запроса вызвать реальный путь LLM и серверного поиска с записью
   usage, действия и выбранных SKU. Не отправлять сообщения в настоящий Telegram
   и не связываться с реальным менеджером: оценивать переход состояния локально.
4. Проверять действие и SKU. Для `clarify` набор кандидатов должен соответствовать
   ожидаемому, без автоматического выбора. Для каждой карточки отдельно сверять
   цену, остаток, единицы и время с SQLite. Проверять отсутствие закрытых полей
   во входах модели, tool results и клиентском ответе.
5. Сохранять ошибки и тайм-ауты как результаты случая. Не удалять неудачные
   попытки и не заменять их лучшими повторами. Сводка содержит число реально
   выполненных случаев и полную стоимость всех попыток.

## Формат отчёта

Сохранить метаданные запуска в `evals/results/<run-id>/metadata.json`, отдельную
строку JSON на случай в `cases.jsonl` и краткую сводку `summary.md`. Эти файлы
создаются только после реального прогона; репозиторий не содержит выдуманных оценок.

Метаданные: `run_id`, `started_at_utc`, `finished_at_utc`, `model`,
`source_revision`, `catalog_sha256`, `cases_sha256`, `prompt_sha256`,
`dependency_versions`, `settings`, `input_usd_per_million`,
`output_usd_per_million`, `total_cost_usd`.

Одна строка результата: `case_id`, `actual_action`, `actual_skus`,
`action_pass`, `sku_pass`, `facts_pass`, `privacy_pass`, `usage` (входные,
выходные и cache-токены), `usage_complete`, `cost_usd`, `cost_ledger`,
`latency_ms`, `error` (null при успехе), `server_cards`, `pass`.
Не сохранять ключи, профили Telegram и закрытые данные каталога.

Порог выпуска: минимум **18/20** однозначных; **10/10** уточнений;
**10/10** неизвестных/вне темы с ожидаемым действием. Все факты и проверки
закрытых полей — **100%**. Невыполненные или ошибочные случаи не считаются
успешными. Отдельно указывать Telegram smoke test и Docker persistence test:
этот набор не доказывает их прохождение.
