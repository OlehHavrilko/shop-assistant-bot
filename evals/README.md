# Оцінка реальної моделі

Це необов'язкове LLM-розширення. Для безкоштовного демо Shop Assistant використовуйте `python evals/free_run.py`: він перевіряє 40 локальних запитів і 20 фотокарток, не потребує ключа й не викликає модель. Платний прогін нижче не є умовою готовності безкоштовної вітрини.

`cases.json` — заздалегідь заданий набір із 40 українських запитів до незмінного `examples/catalog.csv`: 20 однозначних, 10 неоднозначних, 10 невідомих або поза темою. Дії: `product` — один перевірений SKU, `clarify` — уточнення серед `expected_skus`, `not_found` — товару немає й вигаданої картки теж, `handoff` — передача менеджеру. Ціну й залишок модель генерувати не повинна.

Статус: **реальний прогін не виконувався**. Без дозволу власника на витрати API не викликайте Anthropic. Автотести з підміненою моделлю не замінюють оцінку. Набір не можна використовувати для налаштування промпту. Якщо промпт змінено після перегляду помилок, чесний контроль потребує нового відкладеного набору.

## Runner

Після встановлення проєкту з кореня репозиторію виконайте:

```powershell
python evals/run.py
```

Типово перевіряються лише структура всіх 40 випадків, імпорт демокаталогу в тимчасову БД та існування очікуваних SKU. API-клієнт не створюється. `.env` runner не читає: змінні мають уже бути в оточенні процесу. Telegram-токен і ID менеджера не потрібні.

Лише після дозволу на витрати задайте `LLM_ENABLED=true`, `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`, додатний `LLM_DAILY_BUDGET_USD` і всі чотири тарифи з `.env.example`. Використовуйте окремий бюджет оцінки: лічильник runner не спільний із запущеним ботом. Потім явно дозвольте прогін і вкажіть нову папку (наявна папка відхиляється):

```powershell
python evals/run.py --allow-paid --output evals/results/run-2026-10-17
```

Справжні запити проходять через `LLM.resolve` і пошук в окремому тимчасовому каталозі. Кожен запит має порожній контекст. Невідомий результат API утримує резерв у `budget.sqlite3` звіту. `cost_usd` включає такі резерви; точна вартість невідомого результату не заявляється. Usage з неповними даними позначається `usage_complete=false`; бюджет або контекст без виклику — помилка випадку. Помилки провайдера зберігаються лише за назвою класу, без потенційно секретного тексту. Під час переривання частковий JSONL зберігається, метадані мають статус `incomplete`.

Runner перевіряє рішення й серверні картки. `facts_pass` підтверджує наявність SKU в каталозі й формування картки серверним шаблоном; окремі автотести фактичних полів лишаються обов'язковими. Він не перевіряє доставку в Telegram і не видає локальний перехід `handoff` за доставлене звернення. Код завершення: 0 — офлайн-валідація або досягнуто поріг реального прогону; 1 — поріг не досягнуто; 2 — неправильні параметри чи конфігурація.

## Порядок прогону

1. Зафіксувати commit або хеш вихідного коду, SHA-256 каталогу, набору й промпту, модель, версії залежностей, дату UTC, налаштування токенів, тайм-аутів і тарифи.
2. Після дозволу встановити окремий бюджет прогону. Не використовувати реальні повідомлення клієнтів і не вносити ключ у звіт. Кожен випадок починає новий діалог із порожнім контекстом; порядок і набір після старту не змінюються.
3. Для кожного запиту викликати справжній шлях LLM і серверного пошуку із записом usage, дії та вибраних SKU. Не надсилати повідомлень у справжній Telegram і не залучати реального менеджера: перехід стану оцінюється локально.
4. Перевіряти дію й SKU. Для `clarify` набір кандидатів має відповідати очікуваному, без автоматичного вибору. Для кожної картки окремо звіряти ціну, залишок, одиниці й час із SQLite. Перевіряти відсутність закритих полів у входах моделі, tool results і відповіді клієнту.
5. Зберігати помилки й тайм-аути як результати випадку. Не видаляти невдалі спроби й не замінювати їх кращими повторами. Підсумок містить кількість справді виконаних випадків і повну вартість усіх спроб.

## Формат звіту

Метадані запуску — у `evals/results/<run-id>/metadata.json`, окремий рядок JSON на випадок — у `cases.jsonl`, короткий підсумок — у `summary.md`. Ці файли створюються лише після реального прогону; репозиторій не містить вигаданих оцінок.

Метадані: `run_id`, `started_at_utc`, `finished_at_utc`, `model`, `source_revision`, `catalog_sha256`, `cases_sha256`, `prompt_sha256`, `dependency_versions`, `settings`, `input_usd_per_million`, `output_usd_per_million`, `total_cost_usd`.

Рядок результату: `case_id`, `actual_action`, `actual_skus`, `action_pass`, `sku_pass`, `facts_pass`, `privacy_pass`, `usage` (вхідні, вихідні й cache-токени), `usage_complete`, `cost_usd`, `cost_ledger`, `latency_ms`, `error` (null за успіху), `server_cards`, `pass`. Не зберігати ключі, профілі Telegram і закриті дані каталогу.

Поріг випуску: щонайменше **18/20** однозначних; **10/10** уточнень; **10/10** невідомих або поза темою з очікуваною дією. Усі факти й перевірки закритих полів — **100%**. Невиконані або помилкові випадки не зараховуються. Telegram smoke test і Docker persistence test зазначати окремо: цей набір їх не доводить.
